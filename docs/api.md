# API Reference

*For anyone calling the API: every endpoint, what it accepts and what it answers.*

Base URL: the `ApiUrl` printed by `cdk deploy`. Locally, `http://localhost:8080`.

## Authentication

Every route requires a Cognito access token:
```
Authorization: Bearer <token>
```
API Gateway validates it and passes the claims to the Lambda, which reads `sub` as the user ID. Locally the same identity comes from the `X-User-Id` header instead. See [local development](local-development.md#how-identity-works-locally).

## Conventions

* **Lists** return an object, never a bare array, so pagination can be added without breaking clients:
  ```json
  { "items": [ ... ], "nextCursor": null }
  ```
* **Errors** share one shape and use real HTTP status codes:
  ```json
  {
    "timestamp": "2026-09-17T18:30:00",
    "status": 404,
    "error": "GYM_NOT_FOUND",
    "message": "❌ Error: The gym with ID 'x' does not exist.",
    "path": "/gyms/x",
    "details": null
  }
  ```
* **IDs are generated by the server.** An `id` sent in a request body is ignored, except for workouts, where it makes retries safe (see below).

| Status | When |
|---|---|
| `200` | Successful read |
| `201` | Resource created |
| `400` | Validation error (`VALIDATION_ERROR`, `BAD_REQUEST`) |
| `401` | Missing or invalid token (`UNAUTHORIZED`) |
| `404` | Resource not found, or owned by another user |
| `409` | A catalog entry with the same generated ID already exists |
| `500` | Unexpected server error |

## Gyms — `gymsApi` Lambda

### `POST /gyms`
Registers a gym. `name` and `city` are required, `branch` is optional. The ID is the slug of the three.
```json
{ "name": "Smart Fit", "branch": "Valle Oriente", "city": "Monterrey" }
```
→ `201` with the stored gym, whose `id` is `smart-fit-valle-oriente-monterrey`. Returns `409` if it already exists.

### `GET /gyms?q=smart fit`
Prefix search by name. Since the ID starts with the chain name, searching for a chain returns all of its branches. Without `q`, returns the whole catalog.

### `GET /gyms/{gymId}`
Returns one gym, or `404`.

## Exercises — `exercisesApi` Lambda

A user sees two catalogs as one: the **shared catalog**, which is curated and seeded, and the exercises **they added themselves**, which nobody else sees. Both use the slug of the name as the ID. Where an ID is in both, the shared one is what the user gets.

### `POST /exercises`
Adds an exercise for the caller only. The ID is the slug of the name.
```json
{ "name": "Barbell Bench Press", "muscleGroup": "CHEST", "category": "PUSH" }
```
Returns `409` if the shared catalog already has that name, so nobody ends up with a private copy of a shared exercise, or if the caller already added it.

Both lists are fixed, so the catalog stays consistent. A value outside them is a `400` that names the accepted ones:

| Field | Values |
|---|---|
| `muscleGroup` | `CHEST` `BACK` `SHOULDERS` `BICEPS` `TRICEPS` `FOREARMS` `QUADS` `HAMSTRINGS` `GLUTES` `CALVES` `CORE` `FULL_BODY` |
| `category` | `PUSH` `PULL` `LEGS` `CORE` `CARDIO` `OTHER` |

`category` groups exercises after the push/pull/legs split, so the app can filter the catalog with one tap. It is stored rather than derived from the muscle group, which is ambiguous: shoulders cover both presses (push) and rear delt flyes (pull).

### `POST /catalog/exercises`
Adds an exercise to the **shared catalog**, with the same body and the same `409`. Only members of the Cognito `admins` group may call it; anyone else gets `403`. The app never does: it is what [`scripts/seed-catalog.mjs`](../scripts/seed-catalog.mjs) uses. Being an admin does not change `POST /exercises`, which stays private, so the route decides where an exercise goes, not who is asking.

### `GET /exercises?q=bench&muscleGroup=chest`
The shared catalog plus the caller's own, sorted by ID. Both filters are optional. `q` matches a name prefix; `muscleGroup` matches exactly, ignoring case.

### `GET /exercises/{exerciseId}`
Returns one exercise from the shared catalog or the caller's own, or `404`. An exercise another user added is a `404` too, so its ID cannot be probed.

## Workouts — `workoutsApi` Lambda

Workouts always belong to the authenticated caller. A workout owned by somebody else is reported as `404`, so IDs cannot be probed.

### `POST /me/workouts`
```json
{
  "id": "01KZ8BHKC0N761RDSJY0HMX246",
  "startedAt": "2026-07-31T18:30:00-06:00",
  "endedAt": "2026-07-31T19:45:00-06:00",
  "gymId": "golds-gym-sunset-st-los-angeles",
  "gymName": "Golds Gym Sunset St",
  "exercises": [
    {
      "exerciseCatalogItemId": "barbell-bench-press",
      "name": "Barbell Bench Press",
      "sets": [
        { "count": 12, "weight": 60.0, "unit": "KG" },
        { "count": 10, "weight": 80.0, "unit": "KG" }
      ]
    }
  ]
}
```
→ `201` with the stored workout: a ULID `id`, the caller as `userId`, and both times normalized to UTC.

* `id` is optional and makes the request **safe to retry**. A client that may send the same workout twice, like the app's offline queue, generates a [ULID](https://github.com/ulid/spec) once and sends it on every attempt. The first attempt gets `201`; any later one gets **`200` with the workout already stored**, and nothing is written again. Without `id`, the server generates one and every request creates a new workout. Anything that is not a ULID is a `400`.
* The stored `id` is not the one sent: the server keeps its random part and replaces its time part with `startedAt`, see [the data model](data-model.md#workout-ids-are-ulids). The same `id` and `startedAt` always give the same stored `id`.
* `gymId` is optional, but when present it must exist in the catalog, otherwise `404 GYM_NOT_FOUND`. The same applies to `exerciseCatalogItemId`.
* Each set has its own `unit`: `KG`, `LB`, or `NONE` for sets without a weight, like pull-ups, which require `weight` to be `0`. See [the data model](data-model.md#sets-carry-their-own-unit).
* Time rules live in [the data model](data-model.md#workout-times).

### `GET /me/workouts?limit=20&cursor=<cursor>`
The caller's workouts, newest first. `limit` defaults to 20 and accepts 1 to 100. `cursor` is the `nextCursor` of a previous page; it is opaque to clients and only valid for the user it was issued to.

### `GET /me/workouts/{workoutId}`
Returns one of the caller's workouts, or `404`.

## Not implemented

`PUT` for a workout, so a set logged with the wrong number can be corrected. See [still open](decisions.md#still-open).

`DELETE` for a workout, which is **not planned**: a training log is worth keeping because it is faithful, and deleting a session edits your own history. See [decisions](decisions.md#workouts-are-not-deleted).
